# Day 6 — experimental save primitive, NOT integrated

Status: work in progress. `scripts/save/SaveManager.gd` is an isolated persistence primitive; neither the menu nor the game uses it. The actual V0.5 settings, score and tutorial still use their existing files. Do not advertise Continue, persistent progression, migration, atomic gameplay snapshots or power-ups as complete. No data is sent to a server.

The primitive writes a versioned JSON envelope with an SHA-256 of its exact JSON payload to a temporary file under `user://`, verifies it, makes a previous-primary backup using a temporary backup, then renames the new file into place. It reports errors and refuses to overwrite newer-version or unreadable primary/backup files. It can read the backup if the primary is missing, malformed or fails checksum. Backup is the *previous* successful save, not the current one. A first-ever save has no backup until a second successful save. This is an integrity check, not encryption or protection against intentional tampering.

Godot `flush` and file rename do not by themselves prove durable fsync/power-loss guarantees; replacement semantics and failure injection are not tested on Windows, mobile, or Web. Single-writer assumption only; no concurrent save support, locking, or schema validation of game fields. JSON numbers may be parsed as floats: callers must validate, bound and convert explicitly; precision-sensitive RNG/body IDs require a lossless encoding. `legacy_seed` reads old settings, best score and tutorial values without changing them; it is not an installed migration and makes no gameplay save.

Current primitive is **not ready for user saves**.

# V0.6.3.3 DEV — pending Game Over and Rescue checkpoint

Additive validated v3 fields `rescue_remaining` (0/1) and `game_over_pending` (boolean) default to one and false for older v1–v3 snapshots. Downgrading to an older build is not supported: it can ignore or discard these fields. A Game Over cancels merge reservations, pauses and writes a full pending snapshot into the generation power-up checkpoint. `completed_games` is not incremented yet. Continue restores the same pending overlay. On Play Again/Main Menu, a single increment and inactive tombstone are committed together; on New Game from a pending saved session the same increment is applied before the tombstone. Repeat finalization is idempotent in the live instance.

Rescue constructs and validates the complete resulting board with the spent use, cleared Undo snapshot and zero danger timers; its full atomic checkpoint is the commit point. Only after this succeeds does the live board change. An ordinary primary/backup mirror may fail after commit: the higher-generation checkpoint then wins. A deliberately obstructed mirror followed by corrupted primary was tested. A failed checkpoint leaves board and use unchanged. For nonpersistent test fixtures only, disk is bypassed.

This is local, single-writer protection, not anti-tamper or cloud backup. If all local files are deleted, corrupted, or rolled back together, no local scheme can prevent losing or restoring a use. Power-loss/fsync guarantees, simultaneous writers, manual tampering and filesystem/device failures beyond the injected obstructions are not established. A crash before a safe pending checkpoint can revert to the last valid earlier save; a shown save error is not a durable guarantee. Physics contact caches are not serialized. See `QA_REPORT.md` for executed processes and limitations.

# Historical V0.6.2 — collection and statistics integration

The SaveManager versioned envelope remains version 1. Its Classic-session payload is now **session version 2**, containing validated progression version 1 in the same atomic checkpoint as the board, score and RNG. V0.6.1 session-version-1 files remain readable; on the next safe save they migrate to version 2 without clearing the board, best or settings. The V0.6.1 version guard treats session version 2 as future rather than silently discarding new progression; running the older build against this new save was not separately tested. A version newer than 2 or a newer progression version is protected against overwrite. Recovery uses the previous validated primary/backup transaction. If both copies are unreadable/invalid, the UI reports unavailability and the application refuses to replace them automatically.

Progression carries all per-animal counts/dates and lifetime counters. It is written together with the session/tombstone so a restored checkpoint does not replay an already-saved event against separately saved totals. Golden, restart and game-over retain the collection; completed-game tombstones replace both copies. Discovery notifications are transient UI and are not replayed on load. Ineligible old/debug body provenance and `score_untrusted` are retained with the session. See `COLLECTION_REPORT.md` and `STATISTICS_REPORT.md` for migration limits, counting rules and Undo design.

# V0.6.1 — Classic Save / Continue

## Behaviour
- During Classic play a deferred snapshot is attempted roughly once per simulation second; pausing also attempts a save. A snapshot is refused if a drop is uncommitted, a merge is pending/scheduled, or any body is merge-locked. If pause cannot save, return to the menu is blocked with a message; resume and wait for the merge to resolve, or address the storage error. An autosave I/O/validation failure displays a HUD warning and is retried; a pending merge is not treated as a disk error. Restart/new game and game over invalidate the old session. New game asks for confirmation when a usable session exists.
- `user://wild_garden_session.json` has a versioned, SHA-256 checked JSON payload. A temporary file is verified and renamed, with the previous good primary retained as `.bak`. A bad primary falls back to a validated backup. Game-over/new-game tombstones replace both copies so a damaged tombstone does not revive the old session. Unknown newer envelope or session versions are not overwritten. Only local storage is used.
- The validated snapshot contains animal resource ID, per-snapshot identity, position, rotation, linear/angular velocity, sleep state and danger timer; score, best, drop/merge counts, combo and timer, highest tier, current/next, aim/cooldown, tutorial stage and exact RNG state (encoded as a decimal string). On Continue a fresh scene is populated exactly once, only after full validation. No pending pair is serialized. Existing V0.5 best/settings/tutorial files remain in use; this change does not claim a general progression migration.
- Recovery loads the **previous** checkpoint, which can lose recent play. A first-ever saved session may not yet have an active-session backup until the next successful save. Abrupt termination can lose play since the last safe checkpoint; a permanently blocked merge can delay saves. File `flush` and rename are not a demonstrated power-loss durability guarantee, and paired tombstone updates are not a single atomic transaction. Multiple simultaneous writers are unsupported. Physics contact solver internal caches are not serialized, so continuation is not guaranteed bit-identical after subsequent simulation.

## V0.6.3.1 — Remove transaction

The session v2 payload now optionally validates `remove_remaining` as 0 or 1, defaulting missing V0.6.2 values to 1. The candidate snapshot excludes the chosen body and decrements that field. It is written as one checksummed atomic primary checkpoint before live deletion; rejected writes do not consume the use. On success the primary is also copied to the backup using a second save. That secondary operation can fail after the primary has committed; in that event a warning is logged, gameplay is committed, and a later corrupt primary could recover the older backup. Two-process Continue, successful backup recovery, corrupt-file refusal and legacy v2 migration were tested; forced power loss, actual disk-full, simultaneous processes and downgrade to an older build are not established. See `POWERUP_REPORT.md`.

## V0.6.3.2 — snapshot generation and power-up commit record

Session schema 3 adds a monotonic generation, Undo allowance and validated, at-most-one-level Undo snapshot, stable per-body IDs and next-ID counter. Session v1/v2 remains readable; missing Undo fields default to one use and no snapshot, and old Remove balance is preserved. Future session v4 is refused. Generation is local to the save set, not a server ID; simultaneous writers are unsupported.

Alternatives: generation alone cannot prove a newer operation when only an older backup survives; a separate allowance ledger alone cannot reconstruct the corresponding board; two independent files cannot commit atomically without a commit record. Instead, `wild_garden_powerup.json` is a full checksummed, atomically renamed snapshot at the next generation. For Undo/Remove and session tombstones it is written first and is the commit point. Primary/backup mirroring is attempted afterward; a failure there is logged but does not undo the committed action. Load validates all candidates and selects the highest generation, preferring primary for equal generations; a newer journal defeats the older backup. An existing corrupt/unreadable/future journal fails closed. A primary or backup carrying a future schema also blocks overwrite. A normal autosave writes a higher generation primary, so its latest state wins when intact; a prior power-up checkpoint still guards against a stale backup refund.

A test creates actual directory obstructions for checkpoint and backup temporary paths. It verifies that an uncommitted checkpoint failure does not change the live state, and that a committed Undo, Remove and tombstone remain authoritative when backup mirroring fails and the primary is then corrupted. This is not a simulated disk power loss or fsync test. The scheme is not tamper-proof: deletion/loss of the journal can make an older valid backup indistinguishable from a pre-upgrade save, and total local-data loss/corruption cannot preserve usage guarantees. Multiple concurrent processes, external restoration of older save sets, storage hardware durability, older-game downgrade and real mobile/Web/Windows persistence remain untested.
